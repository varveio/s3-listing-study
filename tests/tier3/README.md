# Tier 3 — the FAIL, DRIFT and ERROR verdicts

Tier 1 (`tests/differential/`) replays every committed verdict in the repo. All
57 of them are PASS, so the branch that matters most has no coverage at all: on
any discrepancy the verifier re-lists the reference bucket **before attributing
anything to the tool** (`s3_listing_study.manager.verify.single`, union equivalent in `.union`) and
splits the outcome three ways.

| Re-list says | Verdict | Exit | Means |
| --- | --- | --- | --- |
| agrees with the manifest | `FAIL` | 1 | the bucket did not move — the tool **or this mode's adapter** is wrong |
| disagrees with the manifest | `DRIFT` | 4 | the bucket moved. **Not a tool finding**; the orchestrator re-baselines |
| could not run | `ERROR` | 3 | no attribution is possible. Not a pass |

That split is the fairness mechanism of the whole study, and `FAIL` is the one
output of this codebase that becomes a published finding about another project's
tool — including tools Varve does not maintain, checked by a harness Varve does.
It must be built before the verifier is ported, not after.

## Why it needs a rig at all

A genuine discrepancy drives the verifier into the re-list branch, which calls
`security_preflight` and shells out to `docker run` against real S3. Offline that
dies `rc=3` before any verdict is formed, which is precisely why no receipt in
the repo exercises these paths.

`stage.py` makes them reachable without weakening a check:

- the verifier under test is this checkout's `s3_listing_study.manager.verify`, and
  `test_the_verifier_under_test_is_this_checkouts` asserts that — a stale install
  on the path would otherwise be judged instead. `harness/` is never written to.
- `verifier_entry.py` passes `PreflightSkipped()` through the verifier's
  in-process security seam. Runner readiness is a property of the box, not of
  the implementation under test, and it has its own suite in `harness/tests/`.
  The seam is not installed and no production CLI argument can select it.
- `fake-docker.sh` is installed as `docker` on `PATH` and replays a
  fixture-recorded reference listing. It honours `--prefix`, so a verifier that
  forgot to scope its re-list gets a whole-bucket reference, exactly as it would
  in production.

## The fake runtime contract is implementation-agnostic

The fake docker's entire contract is argv plus three environment variables —
`S3STUDY_FAKE_DOCKER_REFERENCE`, `_RC`, `_STDERR` — and the staged receipts,
manifest and registry are ordinary on-disk artifacts. Nothing in it knows the
verifier is Python. `PreflightSkipped` changes only the readiness check; Docker
execution still goes through the production `SecurityBoundary`, so the fake sees
the exact timeout, network, hardening, and evidence-log argv. The cases, fixtures,
and assertions therefore exercise the shipped verifier while keeping the
mandatory preflight unreachable from a production invocation.

## Fixtures

`tests/fixtures/tier3/` — 45 KB, **synthetic**, generated by `make_fixtures.py`.
This repo commits no third-party listing data: tier 3 tests the verifier's
verdict logic, not the contents of anyone's bucket, and any internally
consistent manifest/payload pair exercises FAIL, DRIFT and ERROR identically.

| File | Content |
| --- | --- |
| `payload-alpha.txt` | 120 rows under `alpha/`, in `s3api ... --output text` shape |
| `payload-beta.txt` | 80 rows under `beta/` — the second shard of the union cases |
| `payload-root.txt` | `catalog.json`, the one key under neither prefix |
| `manifest.tsv` | the canonical form of all 201 rows: the snapshot they verify PASS against |

The shape is what is load-bearing, and every part of it is deliberate: five
contract-v2 fields with each payload row canonicalising to exactly its manifest
row; two non-overlapping shard prefixes; one ROOT-LEVEL key, which is the only
thing that makes STRUCTURAL INCOMPLETENESS reachable, since a union of prefixes
never lists it; and enough rows per shard to move one and leave neighbours.

Values are derived from the key with blake2b, so generation is deterministic and
`tests/test_tier3.py` asserts the committed bytes are exactly what the generator
produces, plus the payload/manifest agreement itself. A hand-edit that broke
either is a failing test rather than a fixture that quietly encodes a mismatch.
Regenerating needs no `$S3_STUDY_DATA`, no network, and works on any checkout.

Every case moves one row: a dropped key, a key the snapshot never had, or an
identical-byte overwrite that changes only the mtime — the case the verifier
calls out at `:878-885`, where the key sets stay identical and any drift check
narrower than the full 5-field record would FAIL a tool that is exactly right.
